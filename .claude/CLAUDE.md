# Claude Code - コード品質ガイドライン

このファイルは、Claude Codeがコード生成する際に従うべき品質基準を定義します。

## 基本方針

- 単に「動くコード」ではなく、**高品質で保守性の高いコード**を生成する
- 文脈（プロトタイプ vs 本番環境）に応じて適切な品質レベルを適用する
- 一貫性のあるコーディングスタイルを維持する

## 8つの品質観点

### 1. エラーハンドリング
- すべての例外を適切に処理する
- ユーザーにとって分かりやすいエラーメッセージを提供する
- エラーの原因と対処方法を明確にする
- try-catchブロックを適切に使用する
- エラーログを記録し、デバッグを容易にする

### 2. セキュリティ
- すべての外部入力を検証・サニタイズする
- 認証・認可を適切に実装する
- 機密情報をハードコードしない（環境変数を使用）
- SQLインジェクション、XSSなどの脆弱性を防ぐ
- 依存ライブラリを最新の安全なバージョンに保つ

### 3. 保守性
- 意味のある変数名・関数名を使用する（略語を避ける）
- 関数は単一責任の原則に従う（1つの関数は1つの役割）
- コードの重複を避ける（DRY原則）
- マジックナンバーを定数化する
- 複雑なロジックには説明的なコメントを追加する

### 4. テスタビリティ
- 依存関係を注入可能にする（DIパターン）
- 純粋関数を優先する（副作用を最小化）
- テストしやすいモジュール構造にする
- モックやスタブを使いやすい設計にする
- ユニットテスト、統合テストを考慮した実装

### 5. パフォーマンス
- 不要なループや計算を避ける
- 適切なデータ構造を選択する
- メモリリークを防ぐ
- 非同期処理を適切に活用する
- N+1問題などの非効率なクエリを避ける

### 6. 信頼性
- エッジケースを考慮する
- null/undefined チェックを適切に行う
- 型安全性を確保する（TypeScriptの型を活用）
- 予期しない入力に対して適切に対処する
- リトライ・フォールバック機構を実装する

### 7. 可観測性
- 重要な処理にはログを出力する
- ログレベル（debug, info, warn, error）を適切に使い分ける
- エラー発生時にはスタックトレースを記録する
- パフォーマンスメトリクスを収集できるようにする
- デバッグしやすい情報を残す

### 8. スケーラビリティ
- 将来の機能拡張を考慮した設計にする
- 拡張に開放、修正に閉鎖（Open/Closed原則）
- インターフェースを使って実装を抽象化する
- プラグイン可能なアーキテクチャを検討する
- 設定の外部化を行う

## コーディング規約

### 命名規則
- **変数・関数**: camelCase（例: `getUserData`, `isValid`）
- **クラス**: PascalCase（例: `UserService`, `DataProcessor`）
- **定数**: UPPER_SNAKE_CASE（例: `MAX_RETRY_COUNT`, `API_ENDPOINT`）
- **真偽値**: `is`, `has`, `can`などの接頭辞を使用（例: `isActive`, `hasPermission`）

### コメント
- **なぜ（Why）**を説明する（何をしているかはコードで分かる）
- 複雑なロジックには必ずコメントを追加
- TODOコメントには日付と担当者を記載
- 公開APIにはJSDocスタイルのドキュメントを記述

### ファイル構造
- 1ファイル1責任（関連する機能をまとめる）
- ファイル名は内容を反映する
- ディレクトリ構造を論理的に整理する

## TypeScript固有のルール

- `any`型の使用を避ける（型を明示する）
- 適切なジェネリクスを使用する
- Union型、Intersection型を活用する
- 型ガードを適切に実装する
- strictモードを有効にする

## Git コミットメッセージ

- 簡潔で分かりやすいメッセージ
- 何を変更したか、なぜ変更したかを明記
- 慣例的なプレフィックスを使用:
  - `feat:` 新機能
  - `fix:` バグ修正
  - `refactor:` リファクタリング
  - `docs:` ドキュメント
  - `test:` テスト
  - `chore:` その他の変更

## レビューチェックリスト

コード生成後、以下を確認する:

- [ ] エラーハンドリングは適切か？
- [ ] セキュリティ上の問題はないか？
- [ ] コードは読みやすく保守しやすいか？
- [ ] テストしやすい構造になっているか？
- [ ] パフォーマンスの問題はないか？
- [ ] エッジケースを考慮しているか？
- [ ] 適切なログを出力しているか？
- [ ] 将来の拡張を考慮した設計か？

## 優先順位

プロジェクトの性質に応じて、以下の優先順位を調整する:

1. **本番環境**: セキュリティ > 信頼性 > 保守性 > パフォーマンス
2. **プロトタイプ**: 保守性 > 信頼性 > その他
3. **ライブラリ開発**: テスタビリティ > 保守性 > スケーラビリティ
