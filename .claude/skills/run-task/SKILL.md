# Run Task スキル

渡された開発タスクを、最初から最後まで一貫した流れで進めるためのスキル。
各ステップで `.claude/rules/` のルールを守る。

> **起動バナー**: 作業を始める前に、最初に `🏃 run-task skill 起動` とだけ1行出力する
> (スキルが動いたことを視認するため)。

## 進め方

### 1. 理解 & 調査
- タスクの目的と完了条件(何ができれば終わりか)を1〜2文で言語化する。
- 関連するファイル・既存の実装・命名やスタイルの慣習を調べる。
- 不明な点や前提が曖昧な場合は、**着手前に質問する**(憶測で進めない)。
- **調査結果は `docs/<ブランチ名>/` に Markdown で書き出す**(例: `docs/feat-add-login/investigation.md`)。
  - `<ブランチ名>` は作業ブランチ名の `/` を `-` に置き換えたもの(例: `feat/add-login` → `feat-add-login`)。
  - まだブランチを切っていない場合は、ステップ2で決めたブランチ名を先に使ってよい。
  - ディレクトリが無ければ作成する。
  - `docs/` は `.gitignore` 済みなのでコミットされない(あくまでローカルの作業メモ)。
  - 記録する内容の例: 目的・完了条件、調べた関連ファイルと役割、既存の慣習、判断の根拠、未解決の疑問。

### 2. プラン
- 変更する対象と手順を短い箇条書きにして提示する。
- 影響範囲・リスク・トレードオフがあれば添える。
- 変更が大きい/複数ファイルに及ぶ場合は、この時点でユーザーの合意を取る。

### 3. ブランチ作成
- `prod` にいる場合は作業ブランチを切る(`.claude/rules/git.md` に従う)。
- ブランチ名は Conventional Commits の type を接頭辞にした kebab-case。
  例: `feat/add-login`, `fix/xxx`, `refactor/xxx`。

### 4. 実装
- 既存コードのスタイル(命名・インデント・コメント量・イディオム)に合わせる。
- 変更は小さく論理的な単位に保つ。
- 破壊的・不可逆な操作の前には確認する。

### 5. 検証
- 変更が実際に意図どおり動くことを確かめる(テスト・型チェック・ビルド・実行など、
  そのプロジェクトで妥当な方法で)。
- ランタイムに影響する変更は、テストだけでなく実際の挙動も確認する。
- 失敗したら原因を直し、通るまで繰り返す。結果は正直に報告する。

### 6. コミット
- Conventional Commits 形式でコミットする(`/commit` 相当)。
- `push` はユーザーが指示したときだけ行う。

## 完了報告

作業後、次を簡潔に伝える:
- 何を変更したか(要点)
- どう検証したか、その結果
- 残課題・フォローアップがあれば

## 連携

- PR まで作りたい場合は、続けて **create-pr** スキルを使う([[create-pr]])。
- コミットだけなら `/commit` コマンドで足りる。
